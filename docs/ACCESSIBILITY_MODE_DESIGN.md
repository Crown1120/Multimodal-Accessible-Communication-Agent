# Bridge 无障碍模式合并与手机式辅助功能方案

> 编写日期：2026-09-15
> 分析基线：`main`，提交 `528b383`
> 文档状态：设计与实施建议，尚未实施代码变更

## 1. 结论

本项目可以把现有“听障”和“视障”合并为一个“无障碍增强”预设，但不建议把所有行为继续硬编码在一个互斥的 `mode` 值中。

推荐采用手机系统常见的两层结构：

1. 顶层只提供少量易理解的辅助功能预设：`标准`、`无障碍增强`、`适老`。
2. 偏好设置中提供独立能力开关，例如实时字幕、高对比度、增强焦点、减少动画和视觉提醒。

这样既能满足“一键进入无障碍模式”的使用习惯，也不会强迫不同用户接受同一套不适合自己的视觉、声音或动画行为。

## 2. 手机系统的参考方式

### 2.1 不存在统一的“听障+视障”标准模式

iOS 和 Android 通常把无障碍能力拆成独立功能：

- 听觉辅助：实时字幕、声音识别、声音/闪光提醒、助听设备支持。
- 视觉辅助：屏幕阅读器、放大、高对比度、增强焦点、文字大小、减少动画。
- 便捷入口：通过辅助功能快捷键、辅助功能菜单或快捷方式，一次启用一组功能。

因此，手机的核心思路不是把听障和视障定义成一个固定用户类型，而是让用户选择一个预设，再按需要微调具体能力。

### 2.2 对 Bridge 的适配

Bridge 是医院/政务沟通工作台，用户通常需要快速完成沟通，不适合展示过多专业选项。建议保留三个明显的预设，同时把复杂选项放到“无障碍偏好”面板中。

推荐的顶层入口：

| 预设 | 面向用户 | 默认行为 |
|---|---|---|
| 标准 | 普通用户 | 默认字号、普通对比度、普通动效 |
| 无障碍增强 | 听障、低视力、光敏或需要辅助操作的用户 | 实时字幕、高对比度、增强焦点、减少动画 |
| 适老 | 老年用户或需要更慢交互节奏的用户 | 大字号、慢速语音、较大点击区域 |

“无障碍增强”不应默认打开闪光提醒，也不应强制慢速语音。闪光和慢速语音应作为独立偏好，避免对光敏用户和不需要慢速语音的用户造成干扰。

## 3. 当前实现中的问题

### 3.1 模式入口是互斥的

**位置**

- `frontend/src/components/ModeSwitcher.vue`
- `frontend/src/types/index.ts`

**现状**

当前入口包含 `standard`、`hearing`、`elderly`、`visual` 四个互斥按钮。用户只能选中一个模式，无法同时组合“字幕 + 增强焦点 + 减少动画”等能力。

**影响**

- 听障用户和低视力用户只能在两个模式之间二选一。
- 具有多种辅助需求的用户无法保留个性化组合。
- 后续增加“减少动画”“屏幕阅读器优化”等能力时，模式枚举会继续膨胀。

### 3.2 模式值同时承担了多个不同职责

**位置**

- `frontend/src/stores/session.ts:91-93`
- `frontend/src/stores/session.ts:385-402`
- `frontend/src/style.css:67-88`
- `frontend/src/style.css:352-397`

**现状**

当前代码将模式同时用于：

- 推导高对比度、大字号和慢速语音；
- 决定是否触发听障闪光通知；
- 切换整套颜色变量；
- 调整按钮、输入框和焦点样式；
- 影响数字人播报参数。

**影响**

一个看似简单的模式切换会产生多个隐含副作用。例如当前所有非标准模式都会推导为慢速语音，但听障用户可能并不需要慢速语音；视障用户也不一定需要黑底黄字或闪光提醒。

### 3.3 当前视障模式不等于完整的视障辅助

**位置**

- `frontend/src/style.css:352-397`
- `frontend/src/components/MessageList.vue`
- `frontend/src/components/SubtitleBar.vue`

**现状**

当前视障模式主要依靠黑色背景、黄色文字、放大焦点和按钮缩放。项目已经有部分 `aria-label`、`aria-live` 和键盘焦点支持，但这些能力没有被抽象成独立功能。

**影响**

- 对低视力用户有效，但对完全依赖屏幕阅读器的用户帮助有限。
- `button:hover` 和 `button:focus` 的缩放行为可能引起布局抖动。
- 高对比度、颜色主题、屏幕阅读器顺序和减少动画混在同一个视觉模式中，难以单独调整。

### 3.4 闪光提醒存在可用性和安全风险

**位置**

- `frontend/src/stores/session.ts:44`
- `frontend/src/stores/session.ts:385-402`
- `frontend/src/views/Workbench.vue:393-402`

**现状**

闪光通知只在 `hearing` 模式启用，当前属于模式隐含行为。

**影响**

- 合并模式后若直接照搬，会把闪光提醒带给所有无障碍用户。
- 光敏用户可能不适合闪烁效果。
- 系统已经支持 `prefers-reduced-motion`，但视觉提醒还没有独立开关。

**建议**

默认使用静态状态变化、边框颜色和 `aria-live` 提示；闪光提醒必须是独立开关，默认关闭，并且在系统偏好为减少动效时强制关闭。

### 3.5 后端模式枚举和记忆服务也需要兼容

**位置**

- `backend/app/models/schemas.py:20`
- `backend/app/models/db_models.py:39`
- `backend/app/memory/service.py:22-36`
- `backend/app/adapters/digital_human.py:183-191`
- `backend/app/agent/state.py:16`
- `docs/PROTOCOL.md:28-30`

**现状**

后端接口目前接受 `standard`、`hearing`、`elderly`、`visual`。数据库使用字符串保存模式，记忆服务和数字人适配器也存在针对 `hearing`、`visual` 的分支。

**影响**

直接删除旧枚举会导致：

- 已保存的旧会话无法恢复；
- 旧客户端请求返回 422；
- 后端模式默认值和数字人语速逻辑不一致；
- 现有 API/集成测试需要大范围修改。

## 4. 推荐的数据模型

### 4.1 顶层模式

新代码使用以下三个预设：

```ts
type AccessibilityMode = 'standard' | 'assistive' | 'elderly'
```

`assistive` 的中文展示名称建议为“无障碍增强”，不要使用“听障+视障”作为用户标签。这样既不会把用户需求简单归类，也更符合手机系统的辅助功能表达方式。

### 4.2 独立能力

建议把需要组合的行为抽成独立偏好：

```ts
interface AccessibilityFeatures {
  captions: boolean
  highContrast: boolean
  enhancedFocus: boolean
  reduceMotion: boolean
  visualAlerts: boolean
  largeFont: boolean
  slowSpeech: boolean
}
```

推荐默认值：

| 能力 | 标准 | 无障碍增强 | 适老 | 说明 |
|---|---:|---:|---:|---|
| 实时字幕 | 否 | 是 | 是 | 字幕内容始终保留在 DOM 中，供屏幕阅读器读取 |
| 高对比度 | 否 | 是 | 否 | 使用可读的对比度组合，不强制黑底黄字 |
| 增强焦点 | 否 | 是 | 是 | 加粗焦点环，不单独依赖颜色 |
| 减少动画 | 否 | 是 | 否 | 停止装饰性循环动画，尊重系统偏好 |
| 视觉提醒 | 否 | 否 | 否 | 需要用户主动开启，避免闪光风险 |
| 大字号 | 否 | 是 | 是 | “无障碍增强”优先放大字幕和关键操作 |
| 慢速语音 | 否 | 否 | 是 | 听障或低视力用户不应被强制使用慢速语音 |

注：表中的“默认”是预设值，不代表用户不能在偏好面板中调整。

### 4.3 模式与能力的关系

模式切换应当是“应用一组默认值”，不是永久覆盖用户的独立选择。建议区分：

- `presetMode`：用户选择的预设，用于显示当前入口状态；
- `features`：用户最终生效的独立能力；
- `systemReducedMotion`：浏览器通过 `prefers-reduced-motion` 返回的系统偏好，优先级高于视觉提醒。

这样用户关闭“闪光提醒”后，再次刷新页面不会因为模式重新计算而被自动打开。

## 5. 兼容迁移方案

### 5.1 过渡期保留旧模式值

第一阶段不要立即删除后端旧枚举。后端暂时接受：

```python
Mode = Literal['standard', 'assistive', 'elderly', 'hearing', 'visual']
```

兼容映射：

```text
hearing -> assistive
visual  -> assistive
```

新前端只创建 `standard`、`assistive`、`elderly`。读取旧会话或旧偏好时，在前端展示层把 `hearing` 和 `visual` 映射为 `assistive`，不立即强制修改旧数据库记录。

这样可以保证：

- 旧客户端仍能创建会话；
- 旧数据库记录仍能读取；
- 新界面只有三个预设；
- 可以逐步更新测试、协议和 Agent 逻辑。

### 5.2 后端默认值迁移

以下位置需要增加 `assistive` 的等价处理：

- `backend/app/memory/service.py` 的模式默认偏好映射；
- `backend/app/adapters/digital_human.py` 的播报行为；
- `backend/app/agent/state.py` 的模式注释和状态定义；
- `backend/app/models/schemas.py` 的请求校验；
- `docs/PROTOCOL.md` 的创建会话示例。

旧模式兼容逻辑应集中在一个 `normalize_accessibility_mode()` 函数中，不要在各个模块重复写 `mode in ('hearing', 'visual', 'assistive')`。

### 5.3 偏好表扩展

如果需要保存独立能力，建议给 `user_preferences` 增加明确字段，例如：

```text
captions_enabled
enhanced_focus
reduce_motion
visual_alerts
```

字段应采用布尔值并设置明确默认值。不要把多个开关序列化到一个 JSON 字段中，否则后端校验、查询和迁移都会变得困难。

## 6. 前端实施边界

### 6.1 `ModeSwitcher.vue`

把四个互斥按钮改为三个预设按钮：

- 标准；
- 无障碍增强；
- 适老。

按钮文案只表达预设，不在按钮上堆叠“高对比度·大字幕”等过多说明。详细能力放到偏好设置中，并保留 `aria-pressed`。

### 6.2 `session.ts`

建议新增统一的能力计算层：

```ts
const isAssistiveMode = computed(() =>
  mode.value === 'assistive' || mode.value === 'hearing' || mode.value === 'visual',
)
```

后续所有样式和行为只依赖 `features` 或 `isAssistiveMode`，不再直接把 `mode !== 'standard'` 当作所有能力的依据。

重点调整：

- `isSlowSpeech` 不再由无障碍增强模式强制开启；
- `flashNotification()` 改为检查 `visualAlerts` 和 `!systemReducedMotion`；
- 切换预设时只应用默认值，不覆盖用户已经单独调整的开关；
- 恢复会话时同时恢复预设和独立能力。

### 6.3 `style.css`

将视觉样式从 `data-mode` 逐步改为能力属性，例如：

```css
[data-contrast='on'] { ... }
[data-focus='enhanced'] :focus-visible { ... }
[data-motion='reduced'] * { ... }
[data-mode='elderly'] { ... }
```

`assistive` 只负责提供安全的默认组合，不应该成为所有样式的唯一选择器。

高对比度设计需要注意：

- 文字、按钮边界和焦点环必须同时满足对比度要求；
- 不仅依赖颜色区分状态；
- 避免 `transform: scale()` 导致按钮和布局抖动；
- 视觉提醒优先使用静态颜色、图标和文本状态。

### 6.4 `PreferencePanel.vue`

建议新增以下独立开关：

- 实时字幕；
- 高对比度；
- 增强焦点；
- 减少动画；
- 视觉提醒。

“闪光提醒”旁边应明确说明这是视觉提醒，而不是无障碍模式的必选能力；关闭后必须能够持久化。

## 7. 实施顺序

### 第一阶段：定义和兼容

1. 增加 `assistive`，保留 `hearing/visual` 输入兼容。
2. 增加统一的旧模式归一化函数。
3. 更新前后端类型、协议文档和模式相关测试。

### 第二阶段：前端预设

1. `ModeSwitcher` 改为三个预设。
2. `session` 拆分预设和独立能力。
3. `PreferencePanel` 增加能力开关。
4. 将 CSS 逐步迁移到 `data-*` 能力属性。

### 第三阶段：听觉和视觉安全

1. 默认关闭闪光提醒。
2. 尊重 `prefers-reduced-motion`。
3. 完善 `aria-live`、按钮名称、焦点顺序和键盘操作。
4. 移除会导致布局抖动的焦点缩放效果。

### 第四阶段：数据收敛

1. 观察旧模式使用情况和兼容日志。
2. 将历史 `hearing/visual` 在读取或写入时逐步归一化为 `assistive`。
3. 确认旧客户端退出支持后，再考虑删除旧枚举。

## 8. 风险与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| 旧会话无法恢复 | 直接删除旧枚举会影响数据库历史记录 | 过渡期保留旧值并在展示层映射 |
| 用户被强制慢速播报 | 当前非标准模式都会推导慢速语音 | 将慢速语音拆成独立开关 |
| 闪光造成不适 | 听障和视障用户不一定适合闪光 | 默认关闭，支持系统减少动效优先级 |
| CSS 规则相互覆盖 | hearing/visual 规则分散在多个文件 | 集中定义能力属性和优先级 |
| 屏幕阅读器体验不完整 | 颜色主题不能替代语义支持 | 保留可读 DOM、ARIA、键盘焦点和 live region |
| 模式切换覆盖用户偏好 | 每次切换都会重置字号和语速 | 预设只初始化未覆盖项，独立设置拥有更高优先级 |

## 9. 验收标准

### 功能

- 模式入口只显示“标准 / 无障碍增强 / 适老”。
- 选择“无障碍增强”后，字幕、高对比度、增强焦点和减少动画按默认值生效。
- 闪光提醒默认关闭，可以独立开启和关闭。
- 关闭某个能力后，切换模式和刷新页面不会无故恢复。
- 旧的 `hearing` 和 `visual` 会话仍能打开，并在界面显示为“无障碍增强”。

### 可访问性

- 模式按钮有正确的 `aria-pressed` 状态。
- 所有开关都有可读名称和当前状态。
- 实时字幕继续使用 `role="status"` 和 `aria-live="polite"`。
- 键盘可以访问模式、偏好开关、输入框和消息操作。
- 开启系统“减少动画”后，不出现闪光和高频循环动画。

### 工程质量

- 前后端不再依赖多个模块分别判断旧模式字符串。
- 新增模式和能力有前端单元测试、后端 API 测试和偏好恢复测试。
- 生产构建、类型检查和关键浏览器交互均通过。
- 协议文档明确新模式、旧模式兼容规则和偏好字段。

## 10. 最终建议

本项目最适合采用“一个无障碍增强预设 + 多个独立能力开关”的方案，而不是继续扩展互斥模式。

短期可以只做前端预设和旧值映射，快速完成界面合并；中期再把字幕、对比度、焦点、动效、视觉提醒和语速全部拆成独立状态；长期再根据真实使用数据决定是否删除 `hearing`、`visual` 旧枚举。

这个方案改动可控、兼容性最好，也更接近手机辅助功能的实际设计方式。
